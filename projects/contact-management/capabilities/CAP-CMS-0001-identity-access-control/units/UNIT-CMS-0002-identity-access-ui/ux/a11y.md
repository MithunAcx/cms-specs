# Accessibility contract — UNIT-CMS-0002 Identity Access UI

WCAG 2.2 AA is the floor. This unit is the one every other role-gated screen sits
behind, so a keyboard- or screen-reader-only failure here blocks every subsequent
screen, not just this one.

## Keyboard map

| Context | Key | Behaviour |
|---|---|---|
| Sign-in form | `Tab` / `Shift+Tab` | Moves between username, password, submit, and (when shown) the retry action, in that visual order |
| Sign-in form | `Enter` | Submits the form from either field, identically to activating the submit control |
| Sign-in form | `Esc` | No effect — there is nothing to dismiss on this view (it is the entry point, not an overlay) |
| Change-password form | `Tab` / `Shift+Tab` | Moves between old password, new password, submit |
| Change-password form | `Enter` | Submits the form from either field |
| Shell — role-gated controls | `Tab` / `Shift+Tab` | Moves through visible controls only; a hidden control is not in the tab order. A visible-and-disabled control (Administrator-only entry point shown to an Editor) **is** reachable by `Tab`, so its caption can be discovered, but activating it (`Enter`/`Space`) has no effect |
| Shell — session-expired banner | `Esc` | No effect — the banner is not dismissible independently of its "Sign in again" action, since dismissing without acting would leave the user on an already-invalid session |
| Global | Arrow keys | Not used anywhere in this unit — no composite widget (listbox, menu, tab strip) exists here |

## Focus order

- **Sign-in, on route entry**: focus moves to the username field.
- **Sign-in, after a credential-rejected error**: focus moves to the password field
  (which was cleared), not to the error message — the message is announced (see
  below) while focus goes where the user's next action is.
- **Sign-in, after a retry-eligible error**: focus moves to the retry action, since
  that is the most likely next step; the error text is announced regardless of
  where focus lands.
- **Change-password, on route entry**: focus moves to the old-password field.
- **Change-password, after the old-password error**: focus moves to the (cleared)
  old-password field.
- **Change-password, after the new-password error**: focus moves to the (cleared)
  new-password field.
- **Change-password, after the retry-eligible error**: focus moves to the retry
  action.
- **Change-password, after success**: focus moves to the confirmation message
  heading (per `60-frontend.md`'s "prefer moving focus to an outcome heading"),
  since the form is gone and there is nothing else on the view to focus.
- **Shell, on the session-expired banner appearing**: focus moves to the banner's
  heading, then to its "Sign in again" action next in tab order — this is the
  terminal-outcome case `60-frontend.md` calls out as always missed.
- **After navigating to sign-in following sign-out or session expiry**: focus
  resets to the username field, same as any other route entry to that view.

## Semantics

| Element | Role | Accessible name |
|---|---|---|
| Sign-in form | `form`, labelled | "Sign in" |
| Username field | `textbox` (native `input`) | "Username" |
| Password field | `textbox` with `type=password` | "Password" |
| Submit button (sign-in) | `button` | "Sign in" (becomes "Signing in" while pending, via the accessible name changing, not only visual text) |
| Credential-rejected error | `alert` (assertive live region) | Its own text is the accessible name; associated with the password field via `aria-describedby` |
| Retry-eligible error | `alert` (assertive live region) | Its own text; the retry action inside it is a separate `button` named "Retry" |
| Offline banner | `status` (polite live region) | Its own text |
| Change-password form | `form`, labelled | "Change password" |
| Old/new password fields | `textbox` with `type=password` | "Current password" / "New password" respectively — never just "Password" twice, since that fails the "must make sense out of context" bar |
| Field-level errors (old/new password) | `alert`, associated via `aria-describedby` on the relevant field | Own text |
| Success confirmation | Heading (`role=heading`, focusable via `tabindex=-1`) | "Your password has been changed." |
| Shell app header | `banner` landmark | "Identity Access UI" (or the product's own header title — this unit only specifies the role/session portion of it) |
| Role badge | Not a live region — static text, part of the header's accessible name context | e.g. "Signed in as Dana Smith, Editor" |
| Sign-out control | `button` | "Sign out" |
| Disabled Administrator-only entry point (shown to an Editor) | `button`, `aria-disabled="true"`, `aria-describedby` pointing at its caption | Its own label plus, via the description, "Requires Administrator role" — never conveyed by disabled-appearance alone |
| Session-expired banner | `alertdialog` — it demands acknowledgement before the redirect, not a passive notice | Its heading text |

## Announcements

| Event | Mechanism |
|---|---|
| Sign-in submitted | No announcement on submit itself; the submit button's own accessible name changes to "Signing in", which a screen reader user tabbing back to it will encounter — no live region needed for a state the user just caused |
| Credential-rejected error | Assertive live region (`alert`) announces immediately on arrival |
| Retry-eligible error (sign-in or change-password) | Assertive live region (`alert`) announces immediately |
| Offline banner appearing/clearing | Polite live region (`status`) — informational, not an interruption |
| Change-password success | Focus moves to the confirmation heading (see Focus order) rather than relying solely on a live region — per `60-frontend.md`'s stated preference, this both announces the result and places the user at what follows it (nothing further, in this case, since the form is gone) |
| Session-expiry banner | `alertdialog` semantics mean it is announced on appearance without a separate live region, and it captures focus until acknowledged |
| Silent refresh in progress (R8/R9) | **No announcement.** Design.md states this is meant to be invisible to the user; announcing an implementation detail the user took no action to trigger would violate "a warning the user cannot act on is worse than silence" (`60-frontend.md`) |

## Visual

- Text contrast ≥ 4.5:1, non-text UI (borders, icons) ≥ 3:1 — both the light and
  dark token pairs reused verbatim from `requirements/contactmanagement-full-mockup.html`
  (see `components.md`) are built to this floor; the mockup does not introduce any
  additional colour.
- All interactive targets (fields, buttons, the retry/sign-out actions) ≥ 24×24 CSS
  px, per the reused `.btn`/`.inp` fixed 36px control height.
- Usable at 200% zoom with no horizontal scroll at 320px — verified against the
  `mobile` (360px) canvas width.
- Respects `prefers-reduced-motion` — moot here: this unit's mockup deliberately
  omits the reference's own `box-shadow`/gradient/`animation`/`transition` (see
  `components.md`'s deviations table), so there is no motion to reduce.
- Colour is never the sole carrier: every error state pairs colour with a labelled
  panel or inline message and text, never colour alone (the error-panel and
  `.help-err` components); the disabled-control caption is text, not merely a
  lower-contrast render.

## Knowingly not covered

- **Password manager / autofill interaction** is not specified — this unit uses
  standard `<input type="password">` semantics, which is the extent a language-
  neutral spec can commit to; autofill behaviour is a browser/engineering concern,
  not a design decision made here.
- **Screen-reader-specific copy for the role badge** beyond the accessible name
  shown above is left to the engineering repo's localisation pass, consistent with
  `60-frontend.md`'s locale note (en/de/fr) — exact phrasing per locale is not
  this unit's decision.
